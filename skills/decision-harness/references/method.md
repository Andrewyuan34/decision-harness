# 方法与证据范围

本工具采用轻量的 PrOACT 结构：问题、目标、选项、后果、取舍。它帮助把一个复杂选择拆成可说明的部分，允许来回修改。它不是要求每个任务都经历一场正式审批，也不是一个自动得出唯一答案的算法。[FWS 的官方课程说明](https://www.fws.gov/training/category/decision-analysis)把 PrOACT 与结构化决策（SDM）作为决策分析培训基础；[USGS 的方法介绍](https://www.usgs.gov/publications/participatory-modeling-and-structured-decision-making)描述了这些步骤及实施环节。

## 标准来自目标，也需要补漏

用户说“想做一个 AI 工具”时，还不知道工具应该怎样才算好。可以先从原话找出他在乎的结果，例如一个人能完成、学到某项能力、减少重复工作。再问每个目标怎样观察，形成这次能使用的标准。

区分三件事：

| 内容 | 例子 | 分析时的作用 |
| --- | --- | --- |
| 想达到的结果 | 现有时间内完成可用版本 | 说明为什么在乎 |
| 实现办法 | 选择依赖较少的方案 | 提出或检查方案，未必适合所有人 |
| 观察依据 | 列出关键任务、已有能力和工时范围 | 判断方案能否达到目标 |

“依赖少”和“完成快”可能有关，但不能默认把它们作为两个独立收益反复计分。同样，学习新技术对成长目标可能是收益，对紧急交付可能是负担。标准必须联系本次目标，而不能只因为在库里就采用。

[Bond、Carlson、Keeney 的 2008 年研究](https://www.scheller.gatech.edu/directory/research/marketing/bond/pdf/bond_carlson_keeney-man-sci-2008.pdf)研究了 MBA 学校和实习等选择。参与者最初列出的目标，遗漏了近半后来从清单中认出与自己相关的目标，遗漏项也有相当重要性。这支持提供补漏帮助，但不能据此宣称所有初学者都漏一半，或 AI 推荐一定更准确。

[同作者 2010 年后续研究](https://www.scheller.gatech.edu/directory/research/marketing/bond/pdf/bond-carlson-keeney-da-2010.pdf)考察了博士选题、MBA 学校与实习选择。第二轮补充思考、类别提示和说明容易遗漏有帮助；少量预设示例并未稳定改善发现过程，还可能让人围绕示例思考。作者建议先独立考虑，再用类别或现有模板补充。这里的轻量适配是：先从用户自己的表达形成目标和初步标准，再用库补漏，而不是要求初学者独立完成整套标准后才能继续。

库中的具体技术项目条目是本项目原创的编辑建议。方法文献启发了组织方式，没有逐条验证这个库，也不为游戏引擎示例背书。个人库可以补充新情境；任何一份库都不能保证列全了人的价值与实际风险。

## 比较依据与人的偏好分开

依据回答“这个候选在该方面表现如何”，偏好回答“这一方面对用户有多重要”。某个 API 是否支持离线使用需要查材料；离线使用是不是必需取决于用户目标。不要让检索频率、资料数量或模型的表达自信代替重要性。

判断可以标为：

- `supported`：目前依据支持这条判断。
- `mixed`：依据或不同情境给出不同方向的结果。
- `concern`：发现了相关问题或代价。
- `unknown`：尚不能判断，并说明缺什么。

它们不是分数。`unknown` 不是零分，`concern` 不自动删除候选。用户明确的硬约束需要单独核对；用户未说是硬约束的偏好，不能被 Agent 悄悄升级为一票否决。

先用可理解的文字和证据比较取舍，必要时给出“若目标是 A，优先考虑 X；若约束是 B，考虑 Y”。[英国多标准分析手册第 5–6 章](https://assets.publishing.service.gov.uk/media/5a790545e5274a2acd18b975/1132618.pdf)区分了基础比较与更正式的分析。v0.1 不提供默认权重或总分；如果用户需要正式量化方法，应明确另行扩展范围与假设，不能假装文字结果已经经过该计算。

## 小试验和检查能说明多少

结构检查只能发现已定义的字段、覆盖和版本依赖问题。它不知道用户所有重要目标，也不会核实引用内容。引用存在、字段完整、程序测试通过，都不等于研究正确。

一次真实 Agent 案例可以显示规则和工具是否能合作完成任务，以及产生的记录是否可检查。它不能证明本工具比普通对话更优，也不能证明初学者更易使用。评价这些效果需要另外设计用户试用和比较研究。

对于游戏引擎案例，样例场景或无界面测试通过，只能支持它实际覆盖的行为。它不自动证明真实游戏中的稳定性、兼容性或体验；具体游戏的目标、约定和验收证据仍然优先。
